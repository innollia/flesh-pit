# 클린룸 플레이테스트: 플레이어는 화면만, 평가자는 증거로

사용자는 플레이 에이전트·자동 피드백 도구 조사 두 편을 주며, 조사 쪽이 방향을 두 번 잘못 잡았으니 걸러서 클린룸 플레이테스트와 피드백 받기를 하자고 했다(2026-10-20).

## 받은 것

- 세 층을 나눈다. 플레이(입력), 증거(화면·텔레메트리·로그), 평가.
- 플레이어 에이전트는 플레이어가 볼 수 있는 것만 받는다(화면, 화면의 글자, 들린 소리의 이름, 조작 안내). 평가자는 텔레메트리·로그·기획 의도까지 본다. 내부 좌표를 보고 길을 찾은 에이전트가 "잘 찾았다"고 판정하는 일을 막는다.
- 빠른 입력은 게임 안에서, 판단은 행동 단위로. 브리지가 프레임마다 실제 입력 이벤트를 넣고, 에이전트는 최대 10초짜리 행동을 고른다. 명령 사이에는 게임 시간이 멈춘다.
- 사건 단위 기록. step마다 명령, 화면, 화면 글자, 소리, 텔레메트리, 플레이어 메모.
- 발견의 형식. 관찰과 추론, 심각도와 확신도를 나누고, 증거가 없으면 가설로 둔다. 에이전트의 인식 실패와 게임의 UX 문제를 텔레메트리로 가른다.
- 격리. 사본은 자기 `user://`를 쓰고, 창은 실제 입력을 받지 않는다. 상태는 엔진에서 명시적으로 내보낸다(메모리를 긁지 않는다).

## 뺀 것

- 외부 서비스(modl.ai, Playloop 등): 빌드·화면·로그가 밖으로 나간다. Playloop은 커밋 몇 개짜리 새 저장소다.
- OS 전체를 조작하는 도구(Cua Driver 등): 설치와 권한이 크다. 이 게임은 엔진 안에서 입력을 직접 넣을 수 있다.
- Unity·Unreal·Minecraft 전용 도구, LangChain·AutoGen: Claude Code 하위 에이전트와 파일 프로토콜로 충분하다.
- Sentry·Grafana: 로컬 로그와 텔레메트리로 충분하다.
- 검증되지 않은 커뮤니티 스킬 설치(gstack-game, MCP Game Helper 등).
- 확인할 수 없는 날짜·버전 주장은 근거로 쓰지 않았다.
- 두 번째 조사의 "AI에게 플레이시키지 말라": 사용자가 플레이테스트를 원했으므로 플레이는 시킨다. 판정은 플레이어 본인이 아니라 증거를 보는 평가자가 한다.

## 클린룸을 지키는 방법

- 가장 강한 방식은 `claude -p`를 방 폴더에서 `--permission-mode dontAsk`, `--setting-sources project`, `--strict-mcp-config`로 돌리고 `Bash(python play.py:*)`와 방 안 Read만 허용하는 것이다(`tools/playtest/run_session.py`).
- 2026-10-20에는 이 기계의 `claude` CLI 로그인이 만료돼 하위 에이전트로 돌렸다. 하위 에이전트는 도구를 막을 수 없으므로, 끝난 뒤 대화 기록의 모든 도구 호출을 검사한다(`tools/playtest/audit_player.py`). 방 밖을 본 호출이 하나라도 있으면 그 회차는 버린다.
- 하위 에이전트에는 하네스가 프로젝트 `CLAUDE.md`와 메모 색인을 문맥으로 넣는다(첫 회차 s1에서 확인). 게임 소개와 구현 조건뿐이고 조작·공략은 없지만, 도구 제한으로는 막을 수 없다. 검사 결과에 이 파일들을 적고, 완전한 클린룸이 필요한 회차는 `claude -p` 방식으로 돌린다.
- 파일을 잠시 숨겨도 소용없었다(s2). 하네스가 세션 시작 때 읽어 둔 내용을 하위 에이전트에 넣는다. 그래서 방 폴더를 작은 git 저장소로 만들고, 그 폴더를 프로젝트로 하는 새 세션에서 플레이시킨다(s3). 새 세션은 이 저장소의 `CLAUDE.md`도 메모도 읽지 않는다.
